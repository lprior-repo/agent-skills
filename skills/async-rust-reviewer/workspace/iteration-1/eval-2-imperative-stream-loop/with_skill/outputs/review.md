```rust
// crates/infra/src/event_processor.rs
use futures::StreamExt;
use std::rc::Rc;

pub async fn process_event_stream(mut stream: impl Stream<Item = Event> + Unpin) {
    let context = Rc::new(ProcessingContext::default());
    let mut results = Vec::new();

    while let Some(event) = stream.next().await {
        if event.is_relevant() {
            let enriched = context.enrich(event);
            let result = process(enriched).await;
            results.push(result);
        }
    }

    Ok(results)
}
```

## PHASE 2: Stream Combinators & Concurrency Primitives

**Status**: FAIL -- LETHAL

**Finding 2.1 (LETHAL)**: Imperative stream loop at line 7 (`while let Some(event) = stream.next().await`). This is the textbook anti-pattern explicitly banned by rule `streams_over_loops`. The code processes events sequentially one at a time, completely wasting I/O concurrency. The correct approach is a combinator pipeline using `.filter()`, `.map()`, and `.for_each_concurrent(N)` or `.buffer_unordered(N)`.

**Finding 2.2 (LETHAL)**: No concurrency bound whatsoever. Events are processed one at a time sequentially, but even if concurrency were added, there is no explicit bound (no `buffer_unordered(N)`, no `for_each_concurrent(N)`, no semaphore). Unbounded concurrency is a denial-of-service vector. Every concurrent operation MUST have an explicit bound.

**Correct pattern** (from references/stream-patterns.md):

```rust
pub async fn process_event_stream(stream: impl Stream<Item = Event> + Unpin) -> Result<Vec<ProcessResult>, Error> {
    let context = Arc::new(ProcessingContext::default());

    stream
        .filter(|e| future::ready(e.is_relevant()))
        .map(|e| context.enrich(e))
        .map(|e| process(e))
        .buffer_unordered(32)  // bounded concurrency, results in completion order
        .collect::<Vec<_>>()
        .await
        .into_iter()
        .collect()
}
```

## PHASE 3: Send + Sync Hygiene & Ownership Design

**Status**: FAIL -- LETHAL

**Finding 3.1 (LETHAL)**: `Rc<ProcessingContext>` on line 5. `Rc<T>` is `!Send`. It is held across `.await` points (line 8: `process(enriched).await`, and line 7: `stream.next().await`). This will fail to compile on a multi-threaded Tokio runtime because the future generated by this async function must be `Send`, but `Rc` inside it makes it `!Send`. Rule `arc_over_rc` is unambiguous: **In async contexts, use `Arc<T>` over `Rc<T>`.**

Additionally, `context.enrich(event)` borrows from `context` (via a method call on `Rc`), and if `enrich` returns a value that borrows from context, that borrow would persist across the `.await` at line 8 -- another potential `!Send` issue and a potential lifetime violation.

**Finding 3.2 (MAJOR)**: `mut results = Vec::new()` on line 6. Mutable accumulation via push in a loop. In a concurrent context, this pattern breaks down. If the function is ever refactored for concurrency (which it must be per Phase 2), this `mut` accumulation will not work. The combinator pipeline approach via `.collect()` eliminates this entirely.

## PHASE 4: Cancellation Safety & Pin Awareness

**Status**: WARN

**Finding 4.1 (MAJOR)**: Cancellation safety concern. If this future is dropped between `context.enrich(event)` (line 8) and `process(enriched).await` completing (line 9), the enriched event has been created but never processed. Whether this matters depends on whether `enrich` has side effects or allocates resources that need cleanup. The pattern of "mutate/prepare then await" without a recovery plan is flagged by rule `cancellation_safe_design`.

**Finding 4.2 (MINOR)**: `+ Unpin` bound on the stream is acceptable since the caller is passing a concrete stream. This is fine and not over-pinned.

## PHASE 5: Observability & Error Propagation

**Status**: FAIL -- MAJOR

**Finding 5.1 (MAJOR)**: No `#[tracing::instrument]` on this async function. This is an infrastructure-layer async function -- the exact place where instrumentation is mandatory. Rule `tracing_instrument` requires every async function in the shell to have instrumentation or explicit span creation. Bare `.await` without surrounding span loses causal chain across async boundaries.

**Finding 5.2 (MAJOR)**: No error handling on `process(enriched).await` (line 9). The result is blindly pushed into `results`. If `process` can fail (which it almost certainly can -- it is doing I/O), the error is silently discarded. Rule `async_error_chain` demands errors be preserved with context. At minimum, this should be `.map_err()` or use `?` propagation.

**Finding 5.3 (CRITICAL)**: No evidence of `console-subscriber` or `tracing-opentelemetry` configuration. Production services MUST expose tokio-console metrics and OTLP traces.

Streams MUST use combinator pipelines (`.filter()`, `.map()`, `.buffer_unordered(N)`, `.for_each_concurrent(N)`). This pattern processes events sequentially, wasting all I/O concurrency. 2. **[Phase 2]** No concurrency bound. Even when refactored to combinators, there is no `buffer_unordered(N)` or `for_each_concurrent(N)`. Unbounded concurrency is a DoS vector. Rule: `bounded_concurrency`.

3. **[Phase 3, line 5]** `Rc<ProcessingContext>` held across `.await` points. `Rc<T>` is `!Send` and will fail to compile on multi-threaded Tokio. MUST be replaced with `Arc<T>`. Rule: `arc_over_rc`.
